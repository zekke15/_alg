# 演算法作業：grep 正規表達式比對（動態規劃 vs. NFA）

## 一、作業目的

對相同的文字搜尋問題使用兩種方法：**動態規劃（DP）**與**非動態規劃（Thompson 型 NFA）**，比較正確性、演算法原理、時間複雜度、空間複雜度和實測效能。

## 二、實作範圍

這是教學用的簡化版 grep，不是完整的 POSIX / PCRE 正規表達式引擎。支援一般字元、`.`（任意一個字元）及 `*`（前一字元重複零次或多次）。`*` 不能放在開頭或連續出現。不支援 `+`、`?`、`|`、括號、跳脫符號與錨點。預設在**整行中的任一位置**搜尋符合的子字串；空模式與能匹配空字串的模式對每一行都視為成功。英文區分大小寫。

## 三、Windows CMD / VS Code 執行方式

請安裝 Python 3.9 以上，解壓縮 ZIP 後開啟資料夾，在 CMD 或 VS Code 終端機輸入：

```bat
cd grep_homework
py main.py
py main.py "ab*c"
py main.py "c.t" sample.txt
py main.py "c.t" sample.txt --benchmark --repeats 100
py -m unittest -v test_grep.py
```

如果沒有 `py` 指令，改成 `python`。CMD 建議將編碼切換為 UTF-8：`chcp 65001`。

內建示範資料包含 `cat`、`cut`、`cot` 等；指定文字檔後可搜尋自備的 UTF-8 文字資料。`sample.txt` 是附帶的示範檔案。

## 四、核心演算法原理

### A. 動態規劃（DP）

令 `dp[i][j]` 表示「模式前 j 個字元是否能匹配文字前 i 個字元的某個後綴」，因此 `dp[i][0] = True`（可在任何文字位置開始）。

- 普通字元或 `.`：若目前字元匹配，`dp[i][j] = dp[i-1][j-1]`。
- `*`：`dp[i][j] = dp[i][j-2] OR (字符匹配 AND dp[i-1][j])`，分別表示重複零次或至少一次。
- 若任意 `dp[i][m]` 為 True，即找到符合模式的子字串。

例如文字 `abbc`、模式 `ab*c`：`b*` 可吃掉兩個 b，最後 c 匹配成功。此方法使用完整的二維布林表。

### B. 非動態規劃：NFA

先將模式編譯為有限狀態機：普通字元使用帶標籤的轉移，`*` 使用 ε 轉移與自迴圈表示「零次或多次」。每讀取一個字元，計算目前活躍狀態的可用轉移，再求 ε 閉包。為支援 grep 子字串搜尋，每個位置允許從初始狀態重新開始。只要活躍集合包含接受狀態，就匹配成功。此方法不儲存 DP 二維表。

## 五、複雜度分析

令 n 為**單次搜尋的文字長度**，m 為模式長度，NFA 狀態數為 O(m)。

| 方法 | 預處理 | 最差搜尋時間 | 額外空間 |
|---|---|---|---|
| DP（完整表格） | O(m) 檢查模式 | O(nm) | O(nm) |
| NFA（本實作） | O(m) 編譯 | O(nm) | O(m) |

兩者最差搜尋時間同階；NFA 的優勢是通常不需要配置完整的 n×m 表格。但 Python 常數開銷、資料內容及匹配提早結束都會影響實際速度，不能保證 NFA 一定更快。

## 六、驗證與效能實驗

1. `py -m unittest -v test_grep.py`：確認固定案例、逐行搜尋、錯誤模式和 300 個隨機一致性測試。
2. `py main.py "c.t" sample.txt --benchmark --repeats 100`：比較同一份文字的兩種搜尋方法。
3. `--benchmark` 會串接全部行為單一文字進行效能測量，**不同於逐行 grep 的語意**；此模式只用來測量字串搜尋函數的成本，不用來計算有多少行符合。基準測試包含 NFA 編譯與 DP 表配置成本。
4. 多次實驗時請固定文字、模式、測試次數和執行環境。短模式或提早匹配容易造成數據不穩，建議使用較長的文字及多次重複。

## 七、比較與結論

DP 使用二維表格表示每一段文字與模式的匹配關係，容易觀察狀態轉移，但額外空間為 O(nm)。NFA 以狀態集合追蹤目前可能匹配的路徑，額外空間為 O(m)，更適合展示有限自動機的應用。兩者均能正確完成本作業限定的簡化正規表達式搜尋。效能優劣應根據實際測試，而非單憑理論判斷。
